# Projects & Tasks API

Лабораторная работа №1 по предмету «Проектирование интеграционных решений».
REST API управления проектами и задачами: CRUD, две версии, API-ключ,
идемпотентность POST, ограничение запросов и OpenAPI.

## Запуск

Нужны Go 1.26.0 или новее и Make. SQLite встроена в приложение: отдельный сервер
БД, Docker и C-компилятор не требуются.

```sh
cd projects/University/API_1
make run
```

При первом запуске на новом компьютере скопируйте `config.example.json` в
`config.local.json` и заполните поле `api_key` своим ключом. Локальный файл
исключён из Git; пример содержит пустое поле ключа. Файл читается из текущей
рабочей директории.

`make run` читает конфигурацию, запускает приложение и автоматически применяет
миграции SQLite. Вводить ключ при каждом запуске не нужно. Непустые переменные
окружения имеют приоритет над файлом; например:

```sh
API_KEY='<your-api-key>' make run # Замените заполнитель своим локальным ключом.
```

По умолчанию
сервер слушает `http://127.0.0.1:8080`, данные сохраняются в `data/api.db`.
Остановка — `Ctrl+C`. Данные и результаты идемпотентности сохраняются после остановки.

- Swagger UI: <http://127.0.0.1:8080/docs>. Введите ключ через **Authorize**.
- OpenAPI: <http://127.0.0.1:8080/openapi.yaml>.

Swagger UI загружает JS и CSS версии 5.31.0 с CDN, поэтому браузеру нужен интернет.
Сам API и файл спецификации работают локально. Документация доступна без ключа.
Ключ хранится только в локальном конфиге или окружении, не выводится в логи
и не сохраняется Swagger UI. Не добавляйте `config.local.json` в репозиторий.

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `API_KEY` | — | Переопределяет `api_key` из локального конфига |
| `HTTP_ADDR` | `127.0.0.1:8080` | Адрес сервера |
| `DB_PATH` | `data/api.db` | Файл SQLite |
| `RATE_LIMIT` | `60` | Запросов в минуту, от 1 до 1 000 000 |
| `LOG_LEVEL` | `info` | Уровень JSON-логов zap |

Дополнительные команды:

```sh
make build # Бинарный файл bin/api; миграции и документация встроены в бинарник.
make lint  # Проверка golangci-lint v2, установленным отдельно.
make fmt   # Форматирование установленным goimports.
```

Автотесты не добавлены. Примеры ниже предназначены для ручной проверки.

## Очистка данных для новой проверки

Остановите сервер через `Ctrl+C`, затем выполните:

```sh
make reset-db
make run
```

`make reset-db` удаляет все проекты, задачи и сохранённые результаты
идемпотентности. Счётчики ID сбрасываются: новые записи снова получают ID от 1.
Схема БД, история миграций и настройки приложения сохраняются. Путь к базе
берётся из `config.local.json`; `DB_PATH` может его переопределить.
После перезапуска сервера также начинается новый отсчёт лимита запросов.

## Структура

Структура основана на [solumD/go-service-template](https://github.com/solumD/go-service-template).

```text
cmd/app/                      точка входа
cmd/reset-db/                 очистка данных для повторной проверки
config/                       локальный JSON-конфиг и переменные окружения
internal/app/                 сборка и запуск приложения
internal/model/               сущности и ошибки
internal/delivery/http/        chi, маршруты v1/v2, DTO и middleware
internal/usecase/              бизнес-правила и последовательные операции
internal/repository/sqlite/    SQL-запросы
pkg/http_server/              таймауты сервера и корректная остановка
pkg/logger/                   настройка zap
pkg/sqlite/                   подключение и применение миграций
migrations/                   SQL-миграции
docs/                         OpenAPI и Swagger UI
```

Поток запроса: HTTP-обработчик → usecase → repository → SQLite.
Версии API используют общие модели, правила и данные; общие обработчики и DTO
не дублируются. DTO обёртки пагинации находится в `v2/dto`.

## Предметная область и контракт

Проект: `id`, `name`. Задача: `id`, `project_id`, `title`, `completed`, `description`.
Связь — один проект ко многим задачам. ID назначается сервером.
Название содержит 1–200 символов после обрезки пробелов по краям, описание — до 2000.

Для каждой версии `/api/v1` и `/api/v2`:

| Метод | Ресурс | Результат |
|---|---|---|
| `POST` | `/projects`, `/tasks` | `201`, объект и `Location` |
| `GET` | `/projects`, `/tasks` | `200`, список |
| `GET` | `/projects/{id}`, `/tasks/{id}` | `200`, объект |
| `PUT` | `/projects/{id}`, `/tasks/{id}` | `200`, обновлённый объект |
| `PATCH` | `/projects/{id}`, `/tasks/{id}` | `200`, объект после частичного обновления |
| `DELETE` | `/projects/{id}`, `/tasks/{id}` | `204`, без тела |

`PUT` полностью заменяет изменяемые поля и не создаёт отсутствующий ресурс.
Для задачи обязательны `project_id`, `title`, `completed`; отсутствие `description`
очищает описание. Задачу можно перенести в другой существующий проект.
Проект с задачами удалить нельзя (`409`). Ссылки проверяются в бизнес-логике
перед изменением данных.

`PATCH` изменяет только переданные поля, остальные сохраняются. Например,
`{"completed":true}` отмечает задачу выполненной, `{"completed":false}` снимает
отметку, а `{"description":""}` очищает описание. `null`, пустой объект, неизвестные
поля и неверные типы возвращают `400`. Новый `project_id` должен указывать на
существующий проект. Для проекта единственное изменяемое поле — `name`, поэтому
его PATCH содержит только новое название. Обе версии возвращают обновлённый объект.

Список задач поддерживает фильтры `project_id` и `completed=true|false`.
Фильтры применяются совместно. Отсутствующий проект в фильтре даёт пустой список.
Сортировка — по ID по возрастанию. Неизвестные и повторные параметры списков запрещены.
JSON-запрос ограничен 64 КиБ; неизвестные поля запрещены.

Ошибки имеют вид:

```json
{"code":"project_not_empty","message":"project contains tasks"}
```

Статусы: `400` — неверный запрос, `401` — нет доступа по ключу, `404` — ресурс
не найден, `405` — метод не поддерживается, `409` — конфликт, `429` — превышение
лимита, `500` — внутренняя ошибка. Подробности внутренней ошибки остаются в логах.

## Развитие API

**Аддитивное изменение:** миграция `001_initial.sql` создаёт задачи без описания,
а `002_task_description.sql` добавляет `description` с пустой строкой по умолчанию.
Старые записи сохраняются. Запросы, не содержащие описание, продолжают работать;
новые клиенты могут передавать дополнительное поле. При запуске новой БД обе
миграции выполняются автоматически, на существующей — только ещё не применённые.

При создании задачи отсутствие или `null` в `completed` означает `false`,
отсутствие или `null` в `description` — пустую строку.

**Несовместимое изменение:** v1 возвращает массив, v2 — объект с пагинацией.

```json
[{"id":1,"name":"Лабораторная работа"}]
```

```json
{"items":[{"id":1,"name":"Лабораторная работа"}],"total":1,"limit":20,"offset":0}
```

В v2 доступны `limit` (1–100, по умолчанию 20) и `offset` (от 0, по умолчанию 0).
`total` учитывает фильтры, но не пагинацию. В v1 пагинации нет.
Смена формы ответа, удаление или переименование полей, изменение типов,
добавление обязательного поля в запрос нарушают контракт старого клиента.
Для таких изменений используется новая версия, а предыдущая остаётся доступной.

## Аутентификация и идемпотентность

Все API-запросы требуют `X-API-Key`. Для учебного интеграционного клиента выбран
API-ключ: он прост в передаче и проверке, не требует регистрации и выпуска токенов.
Приложение использует один ключ и общее пространство данных. Это не система
пользовательских аккаунтов; JWT/OAuth нужны при других требованиях к доступу.
При публикации вне локального компьютера необходимо защищённое HTTPS-соединение.

Каждый POST требует `Idempotency-Key` (1–128 видимых ASCII-символов без пробелов).
Область ключа: клиент, HTTP-метод и путь, включая версию API.

- Те же нормализованные данные и ключ → исходные `201`, тело и `Location`.
- Тот же ключ с другими данными → `409`.
- Ошибка валидации не занимает ключ: после исправления можно повторить запрос.
- Создание ресурса и сохранение результата выполняются последовательными запросами к БД.
- Результат хранится сутки в SQLite, включая перезапуск сервера. Истёкшие записи
  очищаются при обработке POST; после истечения срока ключ можно использовать снова.
- Повтор после удаления ресурса возвращает исходный результат, не восстанавливая
  ресурс. Последующий GET в этом случае вернёт `404`.

Порядок полей JSON, пробелы и явно переданные значения по умолчанию не меняют
смысл повторного запроса. Текущий `X-Limit-Remaining` вычисляется заново.

Идемпотентность рассчитана на последовательные повторы успешно завершённого POST.
Явные транзакции и синхронизация одновременных POST не используются. Сбой между
созданием ресурса и сохранением результата не покрывается этим механизмом.

## Ограничение запросов

Фиксированное минутное окно начинается с первого запроса клиента. По умолчанию
допускается 60 запросов; лимит общий для v1/v2 и всех методов, включая ошибки и
повторы POST. Возвращается `X-Limit-Remaining`. При превышении — `429` и
`Retry-After` с числом секунд до нового окна. Неверные ключи ограничиваются по IP
соединения; заголовки вроде `X-Forwarded-For` не принимаются на доверии.

Счётчики находятся в памяти одного процесса и сбрасываются при перезапуске.
Это учебный сервис с одним экземпляром; для нескольких экземпляров потребуется
общее хранилище счётчиков. `/docs` и `/openapi.yaml` не расходуют лимит API.

## Примеры ручной проверки

В терминале для запросов задайте `API_KEY` равным ключу из локального конфига
или переменной окружения сервера.
Ключи идемпотентности в примерах — идентификаторы операций, а не секреты.

Создать проект (при повторе будет тот же ID):

```sh
curl -i http://127.0.0.1:8080/api/v1/projects \
  -H "X-API-Key: $API_KEY" -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: project-demo-1' \
  -d '{"name":"Лабораторная работа"}'
```

Создать задачу старым запросом без описания. Используйте ID проекта из ответа:

```sh
curl -i http://127.0.0.1:8080/api/v1/tasks \
  -H "X-API-Key: $API_KEY" -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: task-demo-1' \
  -d '{"project_id":1,"title":"Подготовить документацию"}'
```

Ожидаемый ответ на свежей БД:

```json
{"id":1,"project_id":1,"title":"Подготовить документацию","completed":false,"description":""}
```

Создать задачу с новым полем:

```sh
curl -i http://127.0.0.1:8080/api/v1/tasks \
  -H "X-API-Key: $API_KEY" -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: task-demo-2' \
  -d '{"project_id":1,"title":"Проверить API","description":"Проверить обе версии"}'
```

Получить обе формы списка:

```sh
curl -i 'http://127.0.0.1:8080/api/v1/tasks?project_id=1' -H "X-API-Key: $API_KEY"
curl -i 'http://127.0.0.1:8080/api/v2/tasks?project_id=1&completed=false&limit=1&offset=0' \
  -H "X-API-Key: $API_KEY"
```

Отметить задачу выполненной, сохранив остальные поля:

```sh
curl -i -X PATCH http://127.0.0.1:8080/api/v1/tasks/1 \
  -H "X-API-Key: $API_KEY" -H 'Content-Type: application/json' \
  -d '{"completed":true}'
```

Полностью обновить задачу через PUT (описание будет очищено) и удалить её:

```sh
curl -i -X PUT http://127.0.0.1:8080/api/v2/tasks/1 \
  -H "X-API-Key: $API_KEY" -H 'Content-Type: application/json' \
  -d '{"project_id":1,"title":"Подготовить документацию","completed":true}'
curl -i -X DELETE http://127.0.0.1:8080/api/v1/tasks/1 -H "X-API-Key: $API_KEY"
```

Для проверки конфликтов повторите POST с прежним ключом и другим названием;
для проверки доступа выполните GET без `X-API-Key`. Для лимитера остановите сервер,
запустите `RATE_LIMIT=3 make run` и выполните четыре API-запроса: четвёртый вернёт
`429`, `X-Limit-Remaining: 0` и `Retry-After`.

## Вывод

API демонстрирует совместимое расширение схемы и отдельную версию для изменения
формата ответа. Идемпотентность защищает создание ресурсов от повторов,
а rate limiting ограничивает частоту запросов. OpenAPI фиксирует контракт клиента
и сервера. SQLite и один процесс достаточны для локальной демонстрации лабораторной.
