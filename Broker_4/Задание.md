Тема: Проектирование и реализация API на основе очередей сообщений (RabbitMQ)

Цель работы
Изучить подход к проектированию API, работающего через асинхронный обмен сообщениями.
Научиться использовать RabbitMQ как шину взаимодействия между клиентами и сервером, реализуя основные принципы надёжности и масштабируемости API.

Важное замечание
Данная лабораторная работа повторяет по логике первую лабораторную — те же сущности, бизнес-логика и структура API.
Разница заключается в способе взаимодействия: теперь все запросы и ответы передаются через RabbitMQ, а не по HTTP.

Это позволит понять, как проектировать систему, устойчивую к сбоям и способную обрабатывать запросы асинхронно.

Задание
Использовать архитектуру первой лабораторной работы

Основные сущности, операции и структура данных должны остаться такими же, как в лабораторной №1.

Версионность, структура сообщений и логика сохраняются.

Подключить RabbitMQ

Настроить брокер сообщений RabbitMQ.

RabbitMQ можно поднять:

в контейнере Docker (например, rabbitmq:management),

или на виртуальной машине, если это удобнее.

Можно использовать любую конфигурацию, которая обеспечивает обмен сообщениями между клиентом и сервером.

Реализация взаимодействия

Сервер:

принимает запросы из очереди (например, api.requests),

обрабатывает их,

отправляет результаты в очередь ответов (api.responses).

Клиент:

публикует запросы в api.requests,

ожидает ответ в api.responses, используя correlation_id или reply-очередь.

Формат сообщений

Запрос:

{
"id": "uuid",
"version": "v1",
"action": "create_user",
"data": { ... },
"auth": "api-key"
}
Ответ:

{
"correlation_id": "uuid",
"status": "ok",
"data": { ... },
"error": null
}

Идемпотентность

Обеспечить, чтобы повторная обработка одного и того же сообщения не создавала дубликатов.

Можно реализовать через сохранение уже обработанных id запросов в БД или Redis.

Обработка ошибок и надёжность

Реализовать повторную обработку (retry) при временных сбоях.

Настроить Dead Letter Queue (DLQ) для сообщений, вызвавших необрабатываемые ошибки.

Вести журнал ошибок.
